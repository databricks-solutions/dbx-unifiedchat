Core Concepts

AgentRx — Knowledge Base, Index & Genie Spaces

Three concepts sit at the heart of what AgentRx manages. They are easy to conflate but are distinct things: a Genie Space is a data source that lives on the workspace; the knowledge base is the curated set of spaces the multi-agent system is aware of; the index is the searchable, embedded representation that makes the knowledge base usable at query time.

1 · The three concepts at a glance

Genie Space

A Databricks Genie Space — a natural-language-to-SQL workspace over a set of Unity Catalog tables, with its own instructions, sample questions, benchmark questions and per-column settings. It is the source of truth, owned and edited on the workspace, and exists whether or not this app knows about it.

Knowledge Base

The curated set of Genie Spaces the multi-agent system can discover and route questions to — i.e. "what the agent has access to." It is a selection of spaces plus their enriched metadata, not the spaces themselves. A space on the workspace is only in the knowledge base once it has been ingested.

Index

The Databricks Vector Search index built over the knowledge base's enriched metadata. It is how the knowledge base is queried: at runtime the Planning Agent embeds the user's question and searches this index to find the most relevant spaces, tables and columns. The index is a derived, refreshable artifact.

One-line mental model: Genie Spaces are the data sources → the knowledge base is the subset the agent knows about → the index is the embedded form the agent searches.

2 · Membership: a space can be live but not in the knowledge base

Because the knowledge base is a curated selection, the set of Genie Spaces on the workspace and the set in the knowledge base are not the same. This is the distinction AgentRx exists to manage.

On workspace, not indexed

A Genie Space exists but the agent can't discover or route to it. list_genie_spaces shows it; list_indexed_spaces does not. Fix: add_space_to_index.

Indexed (in the KB)

Its enriched chunks are in the tables and the Vector Search index, so the Planning Agent can find and route to it. Appears in both listings.

Removed from index

Chunks deleted from the enriched tables, export files cleaned from the volume, and the index synced — the space is untouched on the workspace but the agent "forgets" it. Tool: remove_space_from_index.

The index is a cache, so it can drift. Editing a Genie Space (new tables, changed instructions, renamed columns — or AgentRx's own benchmark/column edits) does not automatically update the knowledge base. The index reflects the space as of the last enrich/sync. Re-run the metadata refresh (or the incremental add) and a Vector Search sync to reconcile.

4 · How they relate

Genie Spaces are ingested by an ETL pipeline that exports, enriches, chunks and embeds their metadata. The result is the knowledge base, made queryable through the Vector Search index. At query time the agent searches the index, not the spaces directly; it only talks to a Genie Space once the index has pointed it there.

ingest pipeline (build the KB + index) query time (search the index, then use the space)

5 · The ingest pipeline (how a space becomes searchable)

Three ETL stages turn a live Genie Space into indexed, embedded knowledge. AgentRx triggers these (full or incremental) rather than reimplementing them.

Stage 1 · Export
etl/01_export_genie_spaces.py
Pull each Genie Space's config + table metadata from the Genie API and write JSON to the UC Volume (/Volumes/<catalog>/<schema>/volume/genie_exports).
↓
Stage 2 · Enrich + chunk
etl/02_enrich_table_metadata.py
LLM-enrich descriptions, sample values and value dictionaries; write the enriched_genie_docs table, then emit multi-level chunks into enriched_genie_docs_chunks.
↓
Stage 3 · Index
etl/03_build_vector_search_index.py
Build/sync a Delta Sync Vector Search index over each chunk's searchable_content (embedding databricks-gte-large-en, key chunk_id) on endpoint genie_multi_agent_vs.
The incremental path (AgentRx's add_space_to_index) runs stages 2–3 for a single space (stage 1 is done by the tool when it exports that space), so one space can be added without rebuilding the whole index.

6 · What the knowledge base is made of — chunks

Enrichment produces metadata chunks at four levels of granularity. Each chunk is one embedded row in the index, tagged with chunk_type, space_title, table_name, column_name and flags used for filtered search.

chunk_typeGrainWhat it captures
space_summary1 per spaceSpace overview: title, description, and the set of tables it covers.
space_details1 per spaceDeeper space-level context (e.g. instructions / usage guidance).
table_overview1 per tablePer-table description, key columns, temporal hints.
column_detail1 per columnPer-column description, type, value dictionary, identifier/temporal flags.

At query time the Planning Agent can search broadly or filter by chunk_type — e.g. match space_summary chunks to pick the right space, then drill into column_detail chunks for SQL synthesis. "Chunk count" in AgentRx's listings is just how many of these rows a space contributes.
